# Hungerly — API Blueprint

> Status: **Draft for review** (Phase 0). This document defines the API architecture and endpoint catalogue. Nothing here is implemented yet. The machine-readable contract will be the OpenAPI document generated by the FastAPI backend; once it exists it becomes the authoritative contract and this document is kept in sync for intent and rules.

Related: [BLUEPRINT.md](BLUEPRINT.md) · [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md) · [SECURITY.md](SECURITY.md) · [ADR-007](decisions/ADR-007-api-contract.md)

## 1. Principles

1. **REST over HTTPS with JSON.** Resource-oriented URLs, standard verbs, standard status codes. No GraphQL for MVP (see ADR-007).
2. **Versioned in the path:** `/api/v1/...`. Breaking changes go to `/api/v2` while `v1` is supported for a published deprecation window (mobile apps in the field cannot be force-updated instantly).
3. **Surfaces separated by actor.** Each client app talks to its own prefix. Authorization is simpler to reason about and audit, and one app's changes cannot accidentally widen another app's access.

   | Prefix | Used by | Auth |
   |---|---|---|
   | `/api/v1/auth` | all apps | public + token |
   | `/api/v1/me`, `/api/v1/customer/...` | customer app | customer role |
   | `/api/v1/catalog/...` | customer app, public web later | public (optionally authenticated) |
   | `/api/v1/partner/...` | restaurant app | restaurant_staff + membership of that restaurant |
   | `/api/v1/delivery/...` | delivery app | delivery_partner role |
   | `/api/v1/admin/...` | admin dashboard | admin role + admin sub-role |
   | `/api/v1/webhooks/...` | payment/SMS providers | provider signature |
   | `/api/v1/uploads/...` | all apps | token |
   | `/ws/v1` | all mobile apps + admin | token (WebSocket) |
   | `/health/live`, `/health/ready` | load balancer/monitoring | public, no data |

4. **Contract-first where it matters.** Pydantic request/response models are the single definition; the OpenAPI spec is generated from them and typed clients are generated from the spec (Dart for Flutter apps, TypeScript for admin). CI fails if the committed spec drifts from the code.
5. **The server is the source of truth for money, availability and state transitions.** Clients send intent (item ids, quantities, option ids); the server computes prices, fees, discounts and totals.

## 2. Conventions

### 2.1 Requests
- `Content-Type: application/json; charset=utf-8`. Field names are `snake_case`.
- IDs are UUID strings. Timestamps are RFC 3339 in UTC (`2026-09-29T10:15:00Z`).
- Money is an integer in minor units with a currency: `{ "amount_minor": 24900, "currency": "INR" }`.
- Unknown fields are rejected (`extra = forbid`) to catch client bugs early.

### 2.2 Headers
| Header | Direction | Purpose |
|---|---|---|
| `Authorization: Bearer <access_token>` | request | Authentication |
| `Idempotency-Key: <uuid>` | request | **Required** on order placement, payment initiation, refunds and other non-idempotent money operations. Replays within 24 h return the original response |
| `X-Request-ID` | both | Correlation id; generated by the server if absent, always returned |
| `X-Client-App`, `X-Client-Version`, `X-Platform` | request | Analytics, minimum-version enforcement (`426 Upgrade Required` with an update prompt) |
| `If-Match: <version>` | request | Optimistic concurrency for state changes on orders/assignments; mismatch → `409` |
| `Retry-After` | response | On `429` and `503` |
| `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset` | response | Rate-limit visibility |

### 2.3 Pagination
Cursor-based for all lists that can grow (orders, notifications, reviews, admin tables):

```
GET /api/v1/customer/orders?limit=20&cursor=eyJ...
→ { "items": [...], "next_cursor": "eyJ..." | null }
```
Cursors are opaque, signed/encoded `(sort_key, id)` pairs. `limit` default 20, max 100. Admin tables may additionally return `total` when cheap.

### 2.4 Filtering and sorting
Query parameters, e.g. `?status=placed,preparing&sort=-placed_at`. Only explicitly allow-listed fields are filterable/sortable.

### 2.5 Errors
All errors use **RFC 9457 Problem Details** with a stable machine-readable `code`:

```json
{
  "type": "https://docs.hungerly.app/errors/cart-restaurant-conflict",
  "title": "Cart contains items from another restaurant",
  "status": 409,
  "code": "cart.restaurant_conflict",
  "detail": "Your cart has items from 'Spice Route'. Clear the cart to add items from this restaurant.",
  "request_id": "01J9...",
  "errors": [ { "field": "menu_item_id", "code": "restaurant_mismatch", "message": "..." } ]
}
```

| Status | Used for |
|---|---|
| 400 | Malformed request |
| 401 | Missing/invalid/expired access token (`auth.token_expired` triggers client refresh) |
| 403 | Authenticated but not allowed (wrong role, not a member of the restaurant, account suspended) |
| 404 | Resource not found **or not visible to this caller** (avoid leaking existence) |
| 409 | State conflict: invalid transition, version mismatch, duplicate |
| 410 | Resource permanently gone (e.g. expired delivery offer) |
| 422 | Validation failed (field-level `errors[]`) |
| 426 | Client app version below minimum supported |
| 429 | Rate limited |
| 502/503 | Upstream provider failure / maintenance (with `Retry-After`) |

Clients switch on `code`, never on `detail` text. Error codes are listed in the OpenAPI spec.

### 2.6 Realtime
- **WebSocket** `GET /ws/v1?token=<short-lived ws ticket>` (ticket obtained from `POST /api/v1/auth/ws-ticket` to avoid long-lived tokens in URLs/logs).
- Server-to-client events only in MVP (clients use REST for commands). Channels are derived from the user's identity server-side; clients cannot subscribe to arbitrary channels.
- Event envelope: `{ "event": "order.status_changed", "id": "...", "occurred_at": "...", "data": {...} }`.
- Events: `order.status_changed`, `order.eta_updated`, `delivery.location_updated` (customer tracking an active order), `partner.order_created` (restaurant new-order alert), `delivery.offer_created`, `delivery.offer_revoked`, `notification.created`.
- **Push notifications remain the source of alerting** when the app is backgrounded; WebSocket is a live-screen optimisation. Every screen that uses WebSocket also works with polling fallback (REST `GET`) after reconnect.

### 2.7 Webhooks (inbound)
- Signature verified on the **raw body** before parsing; invalid signature → `400` and logged.
- Event stored in `payment_webhook_events` with a unique provider event id; processing is asynchronous and idempotent; the endpoint returns `200` quickly.

## 4. Detailed specifications (important endpoints)

### 4.1 `POST /api/v1/auth/otp/request`
- **Purpose:** Send a 6-digit OTP by SMS for login/signup.
- **Authorization:** Public. Rate-limited per phone (e.g. 3 / 10 min, 10 / day), per IP and per device id; optional CAPTCHA/app-attestation after threshold.
- **Request:** `{ "phone_e164": "+919876543210", "client_app": "customer" | "restaurant" | "delivery", "device_id": "..." }`
- **Response 202:** `{ "otp_request_id": "uuid", "expires_in": 300, "resend_after": 30 }` — identical response whether or not the phone exists (no account enumeration).
- **Errors:** `422 validation.phone_invalid`, `422 auth.phone_not_supported` (non-served country), `429 auth.otp_rate_limited`, `503 auth.sms_unavailable`.
- **Notes:** OTP stored **hashed** in Redis with TTL 5 min, max 5 verify attempts. Admin accounts cannot log in with OTP.

### 4.2 `POST /api/v1/auth/otp/verify`
- **Request:** `{ "otp_request_id": "uuid", "phone_e164": "...", "otp": "123456", "client_app": "customer", "device_id": "...", "device_name": "Pixel 8" }`
- **Response 200:**
  ```json
  {
    "access_token": "<JWT, 15 min>",
    "access_token_expires_in": 900,
    "refresh_token": "<opaque, 30 days sliding, 90 days absolute>",
    "user": { "id": "...", "full_name": null, "roles": ["customer"], "is_new_user": true }
  }
  ```
  First login from the customer app creates `users` + `customer_profiles` + role `customer`. First login from the delivery app creates a `delivery_partners` row in `onboarding`. The restaurant app does **not** auto-create roles; it lists memberships (or starts onboarding).
- **Errors:** `400 auth.otp_invalid` (generic), `410 auth.otp_expired`, `429 auth.otp_attempts_exceeded`, `403 auth.account_suspended`.

### 4.3 `POST /api/v1/auth/login` (admin/staff password)
- **Request:** `{ "email": "...", "password": "...", "client_app": "admin" }`
- **Response 200:** `{ "mfa_required": true, "mfa_token": "<5 min, single use>" }` → client calls `/auth/mfa/verify` with `{ mfa_token, totp_code }` to get tokens.
- **Errors:** `401 auth.invalid_credentials` (generic, constant-time), `423 auth.account_locked` (after repeated failures, with backoff), `403 auth.mfa_enrollment_required`.
- **Admin web token delivery:** refresh token set as `HttpOnly; Secure; SameSite=Strict` cookie scoped to `/api/v1/auth`; access token returned in body and kept in memory. See SECURITY.md.

### 4.4 `POST /api/v1/auth/refresh`
- **Request (mobile):** `{ "refresh_token": "..." }` · **(admin web):** cookie + `X-CSRF-Token` header.
- **Response 200:** new access token + **new** refresh token (rotation). The old one becomes invalid.
- **Errors:** `401 auth.refresh_invalid`; `401 auth.session_revoked` — if a previously rotated token is reused the whole session is revoked (theft detection) and an audit event is written.

### 4.5 `POST /api/v1/customer/addresses`
- **Request:** `{ "label": "home", "line1": "...", "line2": "...", "landmark": "...", "city": "...", "state": "...", "postal_code": "411001", "location": { "lat": 18.52, "lng": 73.85 }, "contact_name": "...", "contact_phone_e164": "...", "delivery_instructions": "..." }`
- **Response 201:** address resource + `{ "serviceable": true, "zone_id": "..." }`.
- **Errors:** `422` field errors; `422 address.limit_reached`. Unserviceable addresses can be saved (`serviceable: false`), since the customer may move later.

### 4.6 `GET /api/v1/catalog/restaurants`
- **Purpose:** Home/discovery listing.
- **Authorization:** Public; if authenticated, favourites are flagged.
- **Query:** `lat`, `lng` (required), `cuisine`, `veg_only`, `min_rating`, `max_delivery_minutes`, `has_offer`, `sort` (`relevance` | `rating` | `delivery_time` | `distance`), `cursor`, `limit`.
- **Response 200:** `{ "items": [ { "id", "slug", "display_name", "cuisines": [...], "rating_avg", "rating_count", "distance_m", "eta_minutes": {"min": 25, "max": 35}, "delivery_fee": {money}, "is_open": true, "next_opening_at": null, "logo_url", "cover_url", "offer_label": "20% off up to ₹100", "is_favorite": false } ], "next_cursor": ... }`
- **Rules:** Only `active` restaurants in the location's zone within `max_delivery_radius_m`. Closed restaurants are returned last, marked `is_open: false`. ETA = prep time + travel estimate (distance-based in MVP).
- **Errors:** `422 validation.location_required`, `200` with empty items + `"serviceable": false` for unserved locations (the UI shows a "not in your area yet" state rather than an error).

### 4.7 `GET /api/v1/catalog/restaurants/{id}/menu`
- **Response 200:** `{ "restaurant_id", "is_open", "categories": [ { "id", "name", "items": [ { "id", "name", "description", "price": {money}, "food_type", "image_url", "is_available", "option_groups": [ { "id", "name", "min_select", "max_select", "options": [ { "id", "name", "price_delta": {money}, "is_available" } ] } ] } ] } ], "menu_version": "etag" }`
- **Caching:** `ETag` + `Cache-Control: public, max-age=60`; Redis-cached per restaurant and invalidated on menu edit/availability change.
- **Errors:** `404 restaurant.not_found` (also for non-active restaurants).

### 4.8 `POST /api/v1/partner/restaurants/{rid}/menu/items`
- **Authorization:** Owner/Manager of `rid`.
- **Request:** `{ "category_id", "name", "description", "price_minor", "food_type", "image_upload_id"?, "is_available", "option_groups": [ { "name", "min_select", "max_select", "options": [ { "name", "price_delta_minor", "food_type"? } ] } ] }`
- **Response 201:** created item with ids.
- **Errors:** `403 partner.not_member`, `403 partner.insufficient_role`, `404 menu.category_not_found` (or belongs to another restaurant), `422` field errors (`price_minor` > 0, `max_select >= min_select`, name length, max 20 groups × 30 options).

### 4.9 `PATCH /api/v1/partner/restaurants/{rid}/menu/items/{id}/availability`
- **Request:** `{ "is_available": false, "until": "2026-09-29T23:59:00+05:30" | null }` (`until` = auto-restock, post-MVP optional).
- **Response 200:** `{ "id", "is_available" }`. Invalidates menu cache; carts containing the item show a warning on next fetch.
- **Errors:** `403`, `404`.

### 4.10 `PATCH /api/v1/partner/restaurants/{rid}/status`
- **Request:** `{ "is_accepting_orders": true }`
- **Errors:** `409 restaurant.not_active` (still in review/suspended), `409 restaurant.outside_hours` (going online outside hours needs an hour exception), `403`.
- **Rule:** A restaurant that ignores N consecutive new orders is automatically set offline (N is an open decision) and the owner is notified.

### 4.11 `GET /api/v1/customer/cart`
- **Response 200:**
  ```json
  {
    "restaurant": { "id", "display_name", "is_open" },
    "items": [ { "id", "menu_item_id", "name", "quantity", "options": [...], "unit_price": {}, "line_total": {}, "is_available": true } ],
    "address": { ... } ,
    "coupon": { "code": "WELCOME50", "discount": {}, "valid": true, "message": null },
    "bill": { "subtotal": {}, "packaging_fee": {}, "delivery_fee": {}, "platform_fee": {}, "tax": {}, "discount": {}, "tip": {}, "total": {} },
    "warnings": [ { "code": "cart.item_unavailable", "cart_item_id": "..." } ],
    "can_checkout": false,
    "blocking_reasons": ["cart.item_unavailable"]
  }
  ```
- **Rules:** The bill is recomputed on every read from live data. `can_checkout` is false if the restaurant is closed/offline, any item unavailable, below minimum order, address missing or unserviceable.

### 4.12 `POST /api/v1/customer/cart/items`
- **Request:** `{ "menu_item_id", "quantity": 1, "option_ids": ["..."], "notes": "less spicy", "replace_cart": false }`
- **Response 200:** full cart (same as GET).
- **Errors:** `409 cart.restaurant_conflict` (items from another restaurant and `replace_cart=false`), `422 cart.options_invalid` (min/max violated or option not of this item), `409 menu.item_unavailable`, `409 restaurant.closed`.

### 4.13 `POST /api/v1/customer/orders`
- **Authorization:** Customer; `Idempotency-Key` header required.
- **Request:** `{ "payment_method": "online" | "cod", "tip_minor": 0, "special_instructions": "...", "expected_total_minor": 34900 }`
- **Behaviour (single DB transaction):** lock cart → re-validate restaurant open/accepting, items available, address serviceable, coupon valid (reserve redemption) → compute bill → if `expected_total_minor` differs, fail so the user can review the new price → create `orders` (+ items/options snapshots, `order_status_events`) → clear cart.
  - `online` → status `pending_payment`; response includes `next_action: "pay"`.
  - `cod` (if enabled for zone/user) → status `placed`; restaurant is notified.
- **Response 201:** `{ "order": { "id", "order_number", "status", "bill", ... }, "next_action": "pay" | "none" }`
- **Errors:** `409 order.price_changed` (includes new bill), `409 cart.empty`, `409 cart.not_checkoutable` (with `blocking_reasons`), `409 coupon.invalid`/`coupon.exhausted`, `422 payment.method_unavailable`, `409 idempotency.key_reused` (same key, different payload).

### 4.14 `GET /api/v1/customer/orders/{id}`
- **Response 200:** order, bill, items, `timeline` (from `order_status_events`), restaurant contact, `delivery`: `{ "partner": { "first_name", "vehicle_type", "rating_avg", "masked_phone" }, "last_location": {lat, lng, at}, "eta_minutes" }` (delivery block only while an assignment is active).
- **Errors:** `404 order.not_found` (also when the order belongs to someone else).

### 4.15 `POST /api/v1/customer/orders/{id}/cancel`
- **Request:** `{ "reason_code": "changed_mind" | "ordered_by_mistake" | "delay" | "other", "comment": "..." }`
- **Rules (proposed, needs business sign-off):** free cancellation while status is `pending_payment` or `placed`; after `preparing`, customer cancellation is not self-service (contact support). Paid orders are refunded automatically.
- **Response 200:** updated order with `payment_status: "refund_pending"` if applicable.
- **Errors:** `409 order.cannot_cancel` (includes current status), `409 order.version_conflict`.

### 4.16 `POST /api/v1/partner/restaurants/{rid}/orders/{id}/accept`
- **Request:** `{ "prep_minutes": 20 }` (bounded 5–90). `If-Match` version header.
- **Behaviour:** `placed → preparing`, sets `accepted_at`, `estimated_ready_at`, `estimated_delivery_at`; enqueues dispatch job; emits `order.status_changed` to customer.
- **Errors:** `409 order.invalid_transition` (e.g. already cancelled by customer), `409 order.version_conflict`, `403`, `404`.
- **Rule:** Orders not accepted within a timeout (e.g. 5 min, open decision) are auto-cancelled with `restaurant_timeout` and refunded.

### 4.17 `POST /api/v1/partner/restaurants/{rid}/orders/{id}/reject`
- **Request:** `{ "reason_code": "item_out_of_stock" | "too_busy" | "closing" | "other", "unavailable_item_ids": [...] }`
- **Behaviour:** `placed → cancelled` (`cancelled_by = restaurant`), refund initiated, coupon redemption released, optionally marks items unavailable.
- **Errors:** `409 order.invalid_transition`, `403`, `404`.

### 4.18 `POST /api/v1/customer/orders/{id}/payments`
- **Authorization:** Customer (own order); `Idempotency-Key`.
- **Preconditions:** order `pending_payment`, not expired.
- **Behaviour:** create a Razorpay order for exactly `orders.total_minor` (server-side amount), store `payments` row `created`.
- **Response 201:** `{ "payment_id", "provider": "razorpay", "checkout": { "key_id": "<public key id>", "provider_order_id": "order_...", "amount_minor", "currency", "prefill": { "contact": "+91..." } } }` — public key id only; **no secret** ever reaches the client.
- **Errors:** `409 order.not_payable`, `409 payment.already_captured`, `502 payment.provider_error`.

### 4.19 `POST /api/v1/customer/orders/{id}/payments/{payment_id}/verify`
- **Request:** `{ "provider_payment_id", "provider_order_id", "provider_signature" }` (from checkout SDK).
- **Behaviour:** verify HMAC signature with the key secret; fetch payment from the provider API to confirm status/amount; mark `captured`; order `pending_payment → placed`. Idempotent with the webhook path (whichever arrives first wins; the second is a no-op).
- **Response 200:** `{ "payment_status": "paid", "order_status": "placed" }`
- **Errors:** `400 payment.signature_invalid` (logged as security event), `409 payment.amount_mismatch`, `202 payment.pending` (provider not final yet; client shows "confirming payment" and relies on webhook/WebSocket).

### 4.20 `POST /api/v1/webhooks/razorpay`
- **Authorization:** `X-Razorpay-Signature` HMAC over raw body with webhook secret.
- **Events handled (MVP):** `payment.captured`, `payment.failed`, `order.paid`, `refund.processed`, `refund.failed`.
- **Response:** `200` after durable storage; processing is async. Duplicate event id → `200` no-op.
- **Errors:** `400 webhook.signature_invalid`.

### 4.21 `PUT /api/v1/delivery/availability`
- **Request:** `{ "is_online": true, "location": { "lat", "lng", "accuracy_m" } }`
- **Errors:** `403 delivery.not_active` (onboarding/suspended), `409 delivery.has_active_assignment` (cannot go offline mid-delivery), `422 delivery.outside_zone`.

### 4.22 `POST /api/v1/delivery/location`
- **Request:** `{ "points": [ { "lat", "lng", "accuracy_m", "speed_mps", "heading", "recorded_at" } ] }` (batch up to 20; sent every ~10 s while online, ~5 s during an active delivery).
- **Behaviour:** latest point → Redis GEO (TTL 2 min, partner considered offline if stale); during an assignment also appended to `delivery_location_pings` and pushed to the customer's live-tracking channel (throttled).
- **Response:** `204`.
- **Errors:** `403 delivery.offline`, `422` invalid coordinates or timestamps too far in the future/past, `429`.

### 4.23 `POST /api/v1/delivery/offers/{assignment_id}/accept`
- **Behaviour:** `offered → accepted` if not expired and the order still needs a partner (row locks + partial unique index guarantee one winner); computes `payout_minor`; notifies restaurant and customer.
- **Response 200:** assignment with pickup/drop details.
- **Errors:** `410 delivery.offer_expired`, `409 delivery.offer_taken`, `409 delivery.already_on_delivery`, `404`.

### 4.24 `POST /api/v1/delivery/assignments/{id}/picked-up`
- **Preconditions:** assignment `accepted`/`arrived_at_restaurant`, order `ready_for_pickup` (or `preparing` if the restaurant forgot to mark ready — allowed, with a flag for ops).
- **Behaviour:** order → `picked_up`; customer notified with live tracking.
- **Errors:** `409 delivery.invalid_transition`, `422 delivery.too_far_from_restaurant` (geofence check, configurable tolerance).

### 4.25 `POST /api/v1/delivery/assignments/{id}/delivered`
- **Request:** `{ "delivery_otp": "4821" | null, "cod_collected_minor": 34900 | null, "location": {...} }`
- **Behaviour:** order → `delivered`; COD amount recorded against the partner (cash reconciliation is an open decision); rating prompt sent to customer.
- **Errors:** `400 delivery.otp_invalid` (if OTP handoff is enabled), `422 delivery.cod_amount_mismatch`, `422 delivery.too_far_from_customer`, `409`.

### 4.26 `POST /api/v1/customer/orders/{id}/rating`
- **Request:** `{ "restaurant_rating": 1-5, "restaurant_review": "...", "delivery_rating": 1-5, "delivery_feedback": "..." }` (each part optional, at least one required).
- **Errors:** `409 rating.order_not_delivered`, `409 rating.window_closed`, `422`.

### 4.27 `POST /api/v1/uploads/presign`
- **Request:** `{ "purpose": "menu_item_image" | "restaurant_logo" | "restaurant_cover" | "restaurant_document" | "delivery_document" | "profile_photo", "content_type": "image/jpeg", "size_bytes": 834221, "owner_id": "<restaurant or partner id>" }`
- **Response 201:** `{ "upload_id", "url", "method": "PUT", "headers": {...}, "expires_in": 300 }`
- **Rules:** content type and size allow-listed per purpose (images ≤ 5 MB; documents PDF/JPEG/PNG ≤ 10 MB); caller must be authorised for `owner_id`; documents go to the **private** bucket; server re-validates magic bytes after upload and strips EXIF from images.
- **Errors:** `422 upload.type_not_allowed`, `422 upload.too_large`, `403`.

### 4.28 `POST /api/v1/admin/restaurants/{id}/approve`
- **Authorization:** Admin(operations). Audit-logged.
- **Request:** `{ "zone_id", "commission_bps": 1800, "note": "..." }`
- **Preconditions:** status `pending_review`; mandatory documents approved.
- **Response 200:** restaurant with `status: active`. Owner notified.
- **Errors:** `409 restaurant.invalid_transition`, `409 restaurant.documents_incomplete`, `422`.

### 4.29 `POST /api/v1/admin/payments/{id}/refunds`
- **Authorization:** Admin(finance); `Idempotency-Key`; audit-logged; amounts above a threshold may require a second approver (post-MVP).
- **Request:** `{ "amount_minor": 12000, "reason": "missing_item", "note": "..." }`
- **Errors:** `409 refund.exceeds_captured`, `409 payment.not_captured`, `502 payment.provider_error`.

## 5. Cross-cutting API behaviour

| Concern | Rule |
|---|---|
| Authorization | Enforced in the service layer via dependency-injected policies (never only in routers or clients). Resource ownership is checked on every access (`order.customer_user_id == caller`) |
| Rate limits | Redis sliding window; tiers in [SECURITY.md](SECURITY.md#rate-limiting) |
| Timeouts | API p95 target < 300 ms for reads; provider calls have explicit timeouts (≤ 10 s) and circuit breaking |
| Idempotency | Redis store keyed by (user, key) with request hash, 24 h TTL; DB unique constraints as the final guard |
| Minimum app version | Configurable per app; `426` with store link |
| Deprecation | `Deprecation` and `Sunset` headers on endpoints scheduled for removal |
| Documentation | OpenAPI served at `/api/docs` in dev/staging only; disabled in production |
